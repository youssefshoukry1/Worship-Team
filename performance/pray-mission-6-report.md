# Mission 6 — Delivery, restore and compatibility

Date: 17 November 2026. Available local verification completed with the swipe recheck described below. Native-device and live-service gates remain open. Nothing deployed.

## Findings and changes

The JavaScript ZIP builder silently omitted unreadable/missing audio, unlike native backup writers. It now fails with a useful error instead of creating an incomplete replacement. Restore now rejects unsupported archive versions and invalid/missing recording references before it writes audio or metadata. Intentionally revoked prayers remain excluded. Existing version-1 archives remain compatible; audio omitted by an older backup cannot be reconstructed.

Extracted the existing VM client fixture into `tests/helpers/prayer-client.cjs` and added a two-client scenario using separate stores/runtimes and mocked transport. It covers offline preparation of text plus two clips, restart, lost send response, retry with the same action ID, anonymous delivery, replay after failed acknowledgement, recipient reply, sender reply/read-state update, duplicate reply, revocation, and restoring an old archive after revocation. Existing tests additionally cover a late reply acknowledgement and deletion during asynchronous delivery/restore.

Added an actual Android archive export using the production `PrayerBackupArchive.build` helper under Robolectric. The saved synthetic-data ZIP is imported by JavaScript, rebuilt, restored again, and replayed without duplicates. It includes legacy IDs, read receipts/replies, queued actions, tombstones, two clips on one prayer, and orphan audio/pending text. Fixture provenance and regeneration instructions are in `tests/fixtures/prayer-archive-provenance.md`.

The iOS archive test is a **synthetic ZIP STORE contract fixture**, not output generated by Swift. Real iOS archive production/import remains an open platform gate.

## Remaining performance work

`scripts/measure-pray-transfer.cjs` measures isolated desktop Chromium work with memory-backed storage and synthetic text. Results: `pray-mission-6-transfer.json`. These are single-run diagnostic measurements, not p95/p99, device frame metrics or end-to-end service latency. Repetitive text compresses unusually well. The test excludes audio, IndexedDB I/O, network, JSON response parsing and object-storage latency.

| Prayers / inbox entries | Backup ms | Restore ms | Inbox merge ms | Inbox timer delay ms |
| ---: | ---: | ---: | ---: | ---: |
| 10 | 5.0 | 3.1 | 1.6 | 1.6 |
| 100 | 7.9 | 7.6 | 1.7 | 1.7 |
| 500 | 29.6 | 23.8 | 10.1 | 11.1 |
| 2,000 | 105.4 | 92.0 | 45.3 | 51.3 |

At 2,000 entries backup/restore timer delays were 106/100.4 ms; inbox JSON was 3,040,891 bytes before audio. The server retrieves all pending transit entries and loads R2 bundles sequentially before returning. List pagination does not bound these separate transport/storage costs.

Proposed [focused follow-ups](../docs/pray-transfer-follow-up-plan.md): **6A worker-based web archive processing**, then **6B bounded inbox transport and ingestion** with a separately reviewed backward-compatible cursor/acknowledgement protocol. Neither is implemented in this mission. Recommend them before the final Mission 7 performance comparison.
